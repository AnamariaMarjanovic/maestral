# ADR-0004: Two-tier design tokens in OKLCH

- **Status:** Accepted
- **Date:** 2026-10-31

## Context

Themes, dark mode and the planned theme generator (ADR-0001) all need to change
how components look without editing components.

## Decision

- **Primitive tokens** hold the raw palette (`--ms-teal-600`, `--ms-gray-50`).
  Only the semantic layer may reference them.
- **Semantic tokens** describe roles (`--ms-color-primary`,
  `--ms-color-text-muted`, `--ms-radius-md`, `--ms-control-height`).
  **Components may only use semantic tokens.**
- Colors are written in **OKLCH**, where the first value is perceptual
  lightness, so shades are generated by changing one number.
- Dark mode uses `color-scheme` plus `light-dark()`: each semantic color names
  its light and dark value in one place. `data-ms-theme` on any ancestor forces
  a scheme.
- Every text/background pair is checked against WCAG 2.2 AA (≥ 4.5:1) in both
  schemes before it is committed.
- Component-internal variables use a `--_` prefix (e.g. `--_bg`) and are not
  part of the public API.

## Alternatives considered

- **Single tier (components use the palette directly).** Rejected: dark mode
  and theming would require per-component overrides.
- **Three tiers (primitive, semantic, component tokens)**, as in PrimeNG.
  Postponed: adds a large public surface early. Can be added later if
  per-component theming is needed.
- **Hex or HSL.** Rejected: HSL lightness is not perceptual, so generated
  shades have uneven contrast.
- **`.dark` class with duplicated variable blocks.** Rejected: `light-dark()`
  keeps both values side by side and follows the OS setting automatically.

## Consequences

- The theme generator only needs to output semantic tokens.
- Adding a component never requires touching the palette.
- OKLCH and `light-dark()` require evergreen browsers.
